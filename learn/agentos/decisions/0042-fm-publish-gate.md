# ADR 0042: The FM Publish Gate — Request Contract, Custody, and the Switch

> A peer seat never publishes to an external social platform and never holds a platform credential.
> Every outbound post begins as one typed, versioned `requestPublish` A2A Task sent by a Fleet seat
> only to the Fleet's registered operator principal (resolved by the Fleet, never caller-supplied;
> for Neo's Fleet, `@tobiu`), keyed by the mailbox-minted `MESSAGE:<uuid>` id and bound to an
> immutable revision content digest (`revisionDigest`). Platform OAuth tokens live exclusively in
> Fleet custody under `<userData>/brain/fleet`, a Fleet-side switch per `peer × channel` governs
> release at publish time behind an operator-authenticated write, and `MailboxService` is the single
> durable publication-state writer with an atomic dispatch reservation so the Fleet-side executor
> publishes at most once.

## Context

In [Discussion neomjs/neo#19500](https://github.com/neomjs/neo/discussions/19500) (*outbound as a measured experiment — hypotheses, attribution, the FM publish gate, and the two-week kill rule*), the operator replaced the original April "Social-MCP" concept (`neomjs/neo-agent-brain#123` Leaf 3, where agent seats would call an MCP server to post directly to social platforms) with a product-grade separation of proposing and publishing ("think of FM as a product"):

1. **No seat ever publishes.** A peer seat drafts a post and sends the Fleet's registered operator principal one typed A2A request (`requestPublish`).
2. **The Fleet Manager is the gate.** The operator's Fleet Manager renders the request card (`Approve · Edit & approve · Reject` with reason) and holds one switch per `peer × channel` (`approve each · approve the batch · auto-approve after a cross-family review attestation · auto-approve`).
3. **A Fleet-side executor publishes under custody.** Platform OAuth tokens live only in Fleet custody (`<userData>/brain/fleet`); `MailboxService` is the single durable writer of the publication state with an atomic dispatch reservation, and the Fleet-side executor reads the switch at publish time and posts at most once under the target account's credential.

During the Discussion's Step 2.5 architectural sweep, @neo-opus-ada's `STEP_BACK` ([`18854629`](https://github.com/neomjs/neo/discussions/19500#discussioncomment-18854629)) and re-read ([`18855553`](https://github.com/neomjs/neo/discussions/19500#discussioncomment-18855553)) identified three cross-repository contracts that had no home in existing Decision Records (`0001`–`0041`), and @neo-gpt-sophie's review ([`18856006`](https://github.com/neomjs/neo/discussions/19500#discussioncomment-18856006), approved at [`18856057`](https://github.com/neomjs/neo/discussions/19500#discussioncomment-18856057)) required a single canonical ADR before implementation so that `neomjs/neo-agent-brain#978`, `neomjs/neo-agent-brain#979`, `neomjs/neo-agent-institution#673`, and `neomjs/neo-agent-skills#168` consume one authority rather than interpreting Discussion folds independently.

### §1. The Request Contract (`requestPublish`)

1. **§1.1 One versioned category.** Outbound publication requests use a single typed A2A message category, `requestPublish` (`taggedConcepts: ['requestPublish']`), carrying a versioned `requestPublish` payload (`schemaVersion: 1`, `channel` ∈ {`x`, `linkedin`}). No second transport or seat-callable MCP server exists.
2. **§1.2 Field list.** Every `requestPublish` payload must supply the following fields, and `MailboxService` must refuse missing required fields, unknown fields, unknown `channel` or `format` values, mutable media references lacking a byte digest, or any embedded credential/secret field with a named reason:
   - `channel`: `'x' | 'linkedin'` — target platform.
   - `account`: non-empty string — target platform account identifier whose credential resides in Fleet custody (e.g., a peer's dedicated X handle, `@neomjs`, or the Neo LinkedIn organization page).
   - `text`: non-empty string — exact post body requested for publication.
   - `media`: array of immutable media reference descriptors (`[]` when text-only). Each entry must supply `{uri, sha256, mimeType}`, where `sha256` is the lowercase hex SHA-256 digest of the **exact media bytes** (or a content-addressed Fleet/artifact reference keyed by that `sha256` byte digest), never a bare mutable URL or file path alone, and never inline credentials or arbitrary executables. Before upload, the Fleet-side executor reads the referenced media bytes, recomputes their SHA-256 byte digest, and verifies that it matches the approved descriptor's `sha256` (refusing on mismatch with `refused: digest`), because hashing an unchanged URL or file path cannot guarantee that the approved media bytes did not change before upload.
   - `hypothesis`: optional non-empty string in the product schema, governed by a Fleet policy flag (`requireHypothesis`, defaulting to `true` for Neo's Fleet and required by working rule for `neomjs/neo#19575`) — when `requireHypothesis` is enabled, `MailboxService` refuses a missing or empty `hypothesis` with a named reason; external Fleet Manager deployments running non-experiment outbound workflows may disable the policy flag without altering the product schema.
   - `format`: `'post' | 'link-reply' | 'reply'` — standalone post, self-reply carrying the external link under the author account's own post (`post` + `link-reply` reach-hypothesis pair on X), or reply to a third-party post. `format` is included in `revisionDigest` (`§1.4`) so a policy-relevant format change cannot reuse an existing approval or attestation.
   - `inReplyTo`: optional non-empty string (required when `format` is `'link-reply'` or `'reply'`, and must be omitted/`null` when `format` is `'post'`) — target provider post id or the already-`published` parent `requestPublish` `MESSAGE:<uuid>` under the same `account` (`§4.4`).
   - `attestation`: optional object `{reviewerMessageId, revisionDigest}` (required for release under the `auto-approve after a cross-family review attestation` switch state; may be supplied at admission or recorded by a later review message per `§1.4`). Any caller-supplied `reviewerFamily` property in the payload is non-authoritative hint metadata and is **never** trusted (`§1.4`, `§3.2`).
3. **§1.3 Identity rule.** The canonical identity of a publish request is **exclusively** the mailbox-minted `MESSAGE:<uuid>` returned by `MailboxService#addMessage` (`ai/services/memory-core/MailboxService.mjs:2835` on `10d9104a`; `:2809` at filing) — **never** an embedded caller-supplied `task.id` (which remains optional, non-authoritative caller metadata) and **never** a per-seat counter.
4. **§1.4 Immutable revisions, public canonicalization, and attestation provenance.**
   - **Public deterministic canonicalization:** A `requestPublish` revision is immutable once recorded. Its `revisionDigest` is the lowercase hex SHA-256 digest over the RFC 8785 (deterministic lexicographically sorted-key UTF-8 JSON) canonicalization of the tuple `{account, channel, format, text, media, inReplyTo: inReplyTo ?? null}`, where each entry of `media` is canonicalized as `{mimeType, sha256, uri}` including its immutable byte digest `sha256`. Because the canonicalization is public and deterministic, a drafting seat, a cross-family reviewer, `MailboxService`, and the Fleet-side executor all compute the identical `revisionDigest` over a draft before or after admission. At admission, `MailboxService` computes `revisionDigest` for `revisionNumber: 1` and returns `{messageId, revision: {revisionNumber, revisionDigest, createdAt, author}}`.
   - **Attestation flows (review-before-admission and later-attestation):**
     1. *Review-before-admission:* A cross-family reviewer computes `revisionDigest` over the canonicalized draft tuple and sends an A2A review message carrying `{revisionDigest}` before the requesting seat submits `requestPublish` with `attestation: {reviewerMessageId, revisionDigest}`. At admission, `MailboxService` reads `reviewerMessageId` from the mailbox store, verifies that the cited message exists and that its attested `revisionDigest` equals `MailboxService`'s computed `revisionDigest`, and refuses admission (`refused: attestation`) if the message is missing or the digest mismatches.
     2. *Later attestation on an existing revision:* After `requestPublish` admission (or after an operator Edit creates `revisionNumber + 1` with a new `revisionDigest`), a cross-family reviewer sends an A2A review message citing `{requestId, revisionNumber, revisionDigest}`. `MailboxService` binds the attestation to that immutable revision only if the revision exists and its `revisionDigest` matches.
   - **Canonical sender and family derivation:** Neither `MailboxService` nor the Fleet-side executor ever trusts a caller-supplied `reviewerFamily` field. Both read the referenced review message (`reviewerMessageId`) from the mailbox store and **derive its sender identity (`from`) and model family through canonical Fleet/roster authority**, verifying that the sender is an authenticated peer seat whose model family is distinct from the requesting seat's model family. Missing review messages, unauthenticated senders, same-family reviewers, or unclassifiable model families are refused with `refused: attestation`.
   - **Approval and attestation invalidation on Edit:** Every operator approval and every cross-family review attestation binds to **one exact `(revisionNumber, revisionDigest)`**. An **Edit** from the operator's Fleet Manager card creates a **new immutable revision** (`revisionNumber + 1`, with its own newly computed `revisionDigest`) under the **same** `MESSAGE:<uuid>` request id, and **inherits neither prior approval nor prior attestation**.
5. **§1.5 Single durable publication-state writer (`MailboxService`) vs. Task states.**
   - **`MailboxService` is the single durable store and sole writer** of the `requestPublish` publication state and revision ledger under the `MESSAGE:<uuid>` request id (no second state copy exists in `ai/services/fleet/`).
   - Legal publication states: `queued` → `publishing` → `published` | `refused` | `unresolved`.
   - `MailboxService` initializes the publication state to `queued` at `requestPublish` admission. Every subsequent publication-state transition (`queued → publishing` dispatch reservation, `publishing → published | refused | unresolved`, and operator reconciliation of `unresolved`) is executed **exclusively through a `MailboxService` transition verb callable only from the Fleet-side executor under operator-bridge authentication** (never callable by agent seats).
   - The A2A Task envelope (`MailboxService.mjs:2965` / `:4796`, routed by `FleetControlBridge.mjs:1464–1480` via `messageId`) transitions `Submitted` → `Completed` (carrying the platform `providerId`) | `Rejected` (carrying the refusal reason) over that durable publication state: `MailboxService` **refuses** any transition of a `requestPublish` Task envelope to `Completed` while its durable publication state is not `published`.
   - The durable publication record in `MailboxService` stores both the **text as requested** (`textAsRequested`, initial seat revision `1`) and the **text as published** (`textAsPublished`, the approved revision's text dispatched to the platform) alongside `{attemptId, revisionNumber, revisionDigest, providerId, readbackAt}` under the request id so the operator edit rate is computable from durable state.
6. **§1.6 Sender, Fleet-resolved operator recipient, wake, and expiry rule.** A `requestPublish` Task may be sent **only** by a registered Fleet seat (`senderPrincipalClass: 'agent'`) and **only** to the **Fleet's registered operator principal** (resolved by the Fleet from Fleet authority, never caller-supplied; for Neo's Fleet, `@tobiu`). `MailboxService` refuses broadcasts (`AGENT:*`), peer-to-peer recipients, and any recipient other than the Fleet's registered operator principal with a named reason. The `requestPublish` category suppresses wake delivery by default (`wakeSuppressed: true` via the mailbox category rule at `MailboxService.mjs:390–432`, as the operator reviews requests in the Fleet Manager inbox card), and the Task envelope's `expiresAt` applies.

### §2. The Custody Rule (`<userData>/brain/fleet`)

1. **§2.1 Single Fleet custody boundary.** Platform OAuth access tokens, refresh tokens, client secrets, and signing keys for X and LinkedIn live **exclusively** in Fleet custody under `<userData>/brain/fleet` (resolved via `AiConfig.fleet.dataDir` / `NEO_FLEET_DATA_DIR`, outside the replaceable application bundle per `neomjs/neo-agent-institution#345` and PR `neomjs/neo-agent-institution#346`).
2. **§2.2 Operator-only placement and X `offline.access` refresh-token rotation.** Credentials enter `<userData>/brain/fleet` only through the operator's one-time interactive browser authorization (OAuth 2.0 user context with PKCE, `tweet.write`, and `offline.access` per X account; LinkedIn Community Management API `w_organization_social` 60-day page-admin token for the Neo organization page). When a stored X access token is expired (`expiresAt <= now`) and an `offline.access` `refreshToken` is present in the custody record, `createFleetCustodyStore` exchanges the refresh token at X's OAuth 2.0 token endpoint (`POST /2/oauth2/token`) and atomically persists the rotated `{accessToken, refreshToken, expiresAt, updatedAt}` record in `<userData>/brain/fleet` (`0o600` file mode) as the sole non-operator write to the custody file; if refresh fails or no `refreshToken` is stored, the store returns `refused: credential` with all secret values scrubbed.
3. **§2.3 Non-exposure invariant.** A platform token, refresh token, or secret **never** appears in an A2A message payload, a Task envelope, a log line, a Memory Core turn or summary, a Native Edge Graph node, `AiConfig`, a git checkout, or any seat workspace or process environment. No executor or bridge verb ever returns or echoes a token; a missing, revoked, or expired token (including LinkedIn's 60-day expiry) produces the named refusal `refused: credential`.
4. **§2.4 Zero seat publishing surface.** No agent seat calls a platform API directly, holds a social credential, or receives an MCP publishing tool.

### §3. The Switch (Fleet-Side Per-Peer × Channel Gate)

1. **§3.1 Fleet-side state behind an operator-authenticated write.** The publish-gate switch is durable Fleet-side state stored in Fleet custody and mutated **only** by the Fleet's registered operator principal (resolved by the Fleet; for Neo's Fleet, `@tobiu`) through an operator-authenticated control-plane write. Component state inside the Fleet Manager UI (`neomjs/neo-agent-institution#673`) is a read-only view and command surface, **never** the switch itself — because UI component state reachable over the Neural Link (`InstanceService#assertWritable` / `admitWrite` in `ai/services/neural-link/InstanceService.mjs`) is a multi-writer coordination lock, not an authorization boundary against connected agent seats.
2. **§3.2 Four legal states per `peer × channel`.** One independent switch exists for each `(peer, channel)` pair (`channel` ∈ {`x`, `linkedin`}), with four states:
   - `approve each` *(mandatory initial default for every `peer × channel`)* — every revision requires an individual operator approval bound to its `revisionDigest` in the FM card before execution.
   - `approve the batch` — the operator reviews and releases a batch of queued revisions for that `peer × channel` in a single explicit action, binding each approval to its displayed `revisionDigest`.
   - `auto-approve after a cross-family review attestation` — the executor may release a queued revision only after verifying a valid `attestation` (`§1.2`, `§1.4`) whose `reviewerMessageId` was read from `MailboxService`, whose sender identity and model family were canonically derived through Fleet/roster authority as distinct from the requesting seat's model family, and whose attested `revisionDigest` matches the revision being published.
   - `auto-approve` — the executor may release a valid `requestPublish` revision for that `peer × channel` without manual per-post click or cross-family attestation, subject to publish-time switch verification, dispatch-time reply-classification and media-digest checks (`§4.2`, `§4.4`), and platform rate/credit guards.
3. **§3.3 Read at publish time.** The Fleet-side executor reads the `(peer, channel)` switch state **at publish time** (immediately prior to acquiring the `publishing` reservation in `MailboxService`), never solely at request admission. If the operator downgrades a switch while requests are `queued`, any queued request whose release condition is below the current switch state is refused (`refused: switch`) and is not published.
4. **§3.4 Mandatory audit trail.** Every change to a switch state is durably recorded beside the switch in Fleet custody with `{who, when, peer, channel, from, to, reason}`.
5. **§3.5 Promotion by the operator's hand only, counted per `peer × channel` pair.** A switch is promoted to a more permissive state **only by the registered operator principal's explicit authenticated action** after the Fleet Manager records an eligibility proposal beside the switch (requiring: at least 10 consecutive batches released **for that exact `peer × channel` pair** with zero operator Edits, platform policy text present in the team's working rules, and the digest-bound attestation check active in code; batches released by other peers on that channel never count toward a peer's pair eligibility). The Fleet Manager's batch/edit counter may record a proposal; it **never** auto-promotes the switch. Downgrading a switch to any stricter state is available to the operator in one click at any time without precondition.

### §4. Publication State, Atomic Dispatch Reservation, and the Executor Contract

1. **§4.1 Executor placement and three operator-bridge verbs.** The Fleet publish executor lives in `ai/services/fleet/` as a sibling to `hostEffects.mjs`, `verifyEffect.mjs`, and `FleetControlBridge.mjs`, and exposes three verbs to the operator-facing Fleet bridge only (never to agent seats):
   - `publish(requestId, revisionDigest)` — executes an approved revision at most once under custody via `MailboxService`'s atomic dispatch reservation (`§4.2`).
   - `readMetrics(providerId)` — reads owned-object metrics (`public_metrics` and `non_public_metrics`: `url_link_clicks`, `user_profile_clicks`, `engagements` within 30 days on X; organization page post statistics on LinkedIn) and returns them tagged with `{source, window, claimClass}`, reporting any unavailable metric as `'unknown'`, never `0`.
   - `reply(...)` — present in the module contract but **disabled** (`§4.4`).
2. **§4.2 Single-writer per-state dispatch table, atomic reservation, and crash reconciliation.** When `publish(requestId, revisionDigest)` is invoked, `MailboxService` and the Fleet-side executor enforce the following explicit per-state rules (no catch-all "otherwise" branch):
   - **`published`:** If the recorded `published.revisionDigest === revisionDigest`, the call is an idempotent no-op returning the recorded `{providerId, revisionDigest, readbackAt}`. If `revisionDigest` differs from `published.revisionDigest` (for example, an attempt to publish another revision on an already-published request), the call is refused (`refused: already-published`) without calling the platform.
   - **`publishing`:** An in-flight or interrupted attempt already holds the active dispatch reservation `{attemptId, revisionDigest, reservedAt}` in `MailboxService`. A concurrent `publish(...)` call **must not** issue a second platform HTTP write; if the prior attempt crashed or timed out, the executor must first run post-crash reconciliation for **that exact reserved `{attemptId, revisionDigest}`** (below) and cannot bypass the reserved attempt with a different digest or newer Edit.
   - **`unresolved`:** Terminal ambiguity until explicit operator reconciliation/resolution. While a request's publication state in `MailboxService` is `unresolved` (retaining `{attemptId, revisionDigest}` of the ambiguous attempt), `publish(...)` **refuses every call** (`refused: unresolved`), including any attempt to approve or dispatch a newly edited revision or another `revisionDigest` on the same request. An `unresolved` attempt cannot be bypassed by another digest or approval, and its `{attemptId, revisionDigest}` must survive until explicit operator resolution.
   - **`refused`:** A refused revision remains `refused` (with its typed reason) unless the operator creates a new immutable revision (`revisionNumber + 1`) via Edit and approves its new `revisionDigest`, or explicitly re-queues a pre-dispatch `refused: credential` / `refused: switch` failure that never issued an external HTTP call.
   - **`queued`:** Proceeds only when all five pre-dispatch gates pass:
     1. **Current revision match:** `revisionDigest` equals the request's latest revision digest (`currentRevision.revisionDigest === revisionDigest`); stale digests from superseded pre-Edit revisions are refused (`refused: digest`).
     2. **Publish-time switch & approval/attestation check:** The executor reads the `(peer, channel)` switch at publish time (`§3.3`) and verifies that `revisionDigest` holds either an explicit operator approval or (under `auto-approve after a cross-family review attestation`) a canonically derived cross-family attestation (`§1.4`, `§3.2`), or that the switch is `auto-approve`.
     3. **Dispatch-time reply-classification check (`§4.4`):** Any revision with `format: 'reply'`, any `format: 'post'` carrying a non-null `inReplyTo`, or any `format: 'link-reply'` whose `inReplyTo` is not proven to belong to the **same publishing `account`** (resolved through that same `account`'s already-`published` parent `requestPublish` receipt in `MailboxService` or verified via an authenticated owned-object read on `request.account`) is refused before reservation with `refused: reply-classification-unresolved`.
     4. **Immutable media byte-digest check (`§1.2`):** For every entry in `media`, the executor reads the bytes to be uploaded, recomputes their SHA-256 digest, and verifies that it matches the approved descriptor's `sha256` (refusing on mismatch with `refused: digest`).
     5. **Atomic dispatch reservation:** Before any external platform HTTP call, the executor acquires an **atomic compare-and-set reservation in `MailboxService`** transitioning `queued → publishing` conditioned on `state === 'queued'` and `currentRevision.revisionDigest === revisionDigest`, durably recording `{attemptId, revisionDigest, reservedAt}`. Concurrent approvals or duplicate clicks cannot both win the reservation or both dispatch.
   - **Post-crash reconciliation and negative recent-posts search:** When reconciling a reserved `publishing` attempt `{attemptId, revisionDigest}` after a crash, timeout, or ambiguous HTTP response, the executor reads the target account's recent posts and checks for the reserved revision:
     - If the matching post is observed on the account, the executor adopts its `providerId`, writes `published` (`{attemptId, providerId, readbackAt, revisionDigest, textAsRequested, textAsPublished}`) in `MailboxService`, and transitions the Task envelope to `Completed` without sending a second post.
     - **A negative, rate-limited, or incomplete recent-posts search is NOT proof that the platform write never happened** (because of platform pagination windows, eventual consistency, or read failures). Whenever a platform HTTP request was initiated (or may have been initiated after `publishing` was reserved) and recent-posts reconciliation does not positively locate the post, `MailboxService` **must** transition `publishing → unresolved` (preserving `{attemptId, revisionDigest}`) and **never** reset to `queued` or replay the post automatically.
3. **§4.3 Publication receipt vs. generic Task completion.** Generic A2A Task `Completed` carries no independent proof of publication. The authoritative publication receipt is the durable `published` state in `MailboxService` holding `{attemptId, providerId, readbackAt, revisionDigest, textAsRequested, textAsPublished}` written only through the Fleet-executor transition path after platform confirmation (or positive post-crash reconciliation), and `MailboxService` refuses `Completed` while publication state is not `published` (`§1.5`).
4. **§4.4 Dispatch-time reply-classification enforcement and disabled `reply` verb.** Until X's automation classification of an operator-approved API reply to a third-party post is established against the primary source in **Falsifier 1** (`§Falsifiers`):
   - The executor's separate `reply(...)` verb ships **disabled** and refuses every call with `refused: reply-classification-unresolved`, naming `https://help.x.com/en/rules-and-policies/x-automation`.
   - At the `publish(requestId, revisionDigest)` dispatch boundary (`§4.2`), the executor enforces the same rule: any revision with `format: 'reply'` is refused (`refused: reply-classification-unresolved`), and any revision with `format: 'link-reply'` is permitted **only** when the executor proves that `inReplyTo` belongs to the **same publishing `account`** (by resolving `inReplyTo` against an already-`published` parent `requestPublish` receipt in `MailboxService` with `parent.account === request.account` and `parent.channel === request.channel`, or by verifying ownership of the target provider post id under `request.account`). The caller's `'link-reply'` label is never trusted; unknown or third-party targets are refused with `refused: reply-classification-unresolved`.

## Consequences

### Positive

- **Credential and direct-API isolation by construction:** No agent seat holds a social token or can call a platform API directly; every outbound request enters `MailboxService` as a typed `requestPublish` Task to the Fleet's registered operator principal (`wakeSuppressed: true`) and can be released only by the Fleet-side executor according to the active `(peer, channel)` switch policy, digest-bound approval/attestation, and dispatch guards. (Under `approve each` or `approve the batch`, a submitted request awaits explicit operator release; under `auto-approve after a cross-family review attestation` or `auto-approve`, a valid request that satisfies the active policy can proceed to publication through the executor, which is why promotion to those states is gated by `§3.5` and revocable in one click under `§3.3`.)
- **Single contract across Brain, Institution, and Skills:** `neomjs/neo-agent-brain#978` (`MailboxService` category, `revisionDigest`, single durable publication-state writer, and atomic reservation), `neomjs/neo-agent-brain#979` (executor), `neomjs/neo-agent-institution#673` (FM card and switch UI), and `neomjs/neo-agent-skills#168` (widening the existing `blog-post` skill trigger and adding load-on-demand `references/outbound-post.md`, with no new skill) implement one field list, one identity rule (`MESSAGE:<uuid>`), one revision-digest rule, and one publication state machine.
- **Zero duplicate posts on concurrent approval, crash, or retry:** Atomic `queued → publishing` reservation in `MailboxService` plus terminal `unresolved` when post-crash recent-posts reconciliation cannot prove the outcome prevents double-posting across network drops or duplicate clicks.
- **Measurable edit-rate and attribution ledger:** Storing both `textAsRequested` and `textAsPublished` alongside `hypothesis` and `providerId` makes the two-week experiment (`neomjs/neo#19575`) and the per-`peer × channel` 10-batch zero-edit promotion gate computable from durable state.

### Costs and Operational Constraints

- **One-time and periodic operator OAuth ceremonies:** The operator must authorize each X account once via browser PKCE (`offline.access`) and re-authorize the LinkedIn organization page token every 60 days until partner refresh-token access exists.
- **`unresolved` requires human inspection and blocks bypass:** When a network failure occurs mid-publish and recent-posts reconciliation does not positively locate the post, the request transitions to `unresolved` (recording `{attemptId, revisionDigest}`) and refuses further automatic retries or new-digest bypasses until the operator reconciles it.
- **X per-request pricing vs. reach hypothesis (`$0.215` for `post` + `link-reply`):** Under X's cited per-request rates (`$0.015` for a plain post without a URL; `$0.200` for a post containing a URL), a plain main post (`$0.015`) followed by a link-bearing self-reply (`$0.200`, since the self-reply carries the URL) costs **`$0.215` under those stated rates** (compared to `$0.200` for a single link-bearing post, not `$0.03`). The `post` + `link-reply` format pair exists to test the **reach hypothesis** (whether keeping external links out of the main post body avoids feed down-ranking, measured as a format variable in `neomjs/neo#19575`), not as a credit cost saving.

## Falsifiers

1. **Falsifier 1 — Unresolved X Reply Classification and Relabelled Third-Party Targets (AC-3, §4.2, §4.4):**
   - **Unresolved question:** Whether an API reply (`POST /2/tweets` with `in_reply_to_tweet_id` targeting a third-party account's post) drafted by an AI seat and explicitly approved by the human operator in the Fleet Manager is classified under X's rules as prohibited automated reply/mention activity in the absence of recipient opt-in or prior written approval from X.
   - **Primary source to verify against:** [X Automation Rules (`https://help.x.com/en/rules-and-policies/x-automation`)](https://help.x.com/en/rules-and-policies/x-automation) or prior written approval from X on the developer application.
   - **Binding rule and falsification condition:** This record **refuses to settle the classification by inference**. Until verified against the primary source above or written approval from X, both the executor's `reply(...)` verb (`§4.1`, `§4.4`) and the `publish(requestId, revisionDigest)` dispatch path (`§4.2`, `§4.4`) refuse any third-party reply with `refused: reply-classification-unresolved` naming `https://help.x.com/en/rules-and-policies/x-automation`. This ADR is falsified if `publish(...)` dispatches a `format: 'reply'` request or a `format: 'link-reply'` request whose `inReplyTo` target is not proven to belong to the same publishing `account` (a relabelled third-party target).
2. **Falsifier 2 — Zero Seat Write Capability (AC-1):**
   - **Falsification condition:** This ADR is falsified if any agent seat ever needs a direct social-platform write capability, an MCP publishing tool, or read access to a platform credential to operate the publish gate or execute `neomjs/neo#19575`.
3. **Falsifier 3 — Neural Link Reachability of the Switch (§3.1):**
   - **Falsification condition:** This ADR is falsified if a seat or Neural Link client can alter the effective `(peer, channel)` switch state by mutating Neo.mjs component state or state-provider properties without an operator-authenticated Fleet control-plane write.
4. **Falsifier 4 — Digest-Unbound Approval, Mutable Media Bytes, Unverified Attestation Family, or Unreconciled/Bypassed Retry (§1.2, §1.4, §3.2, §4.2):**
   - **Falsification condition:** This ADR is falsified if (a) an operator Edit or a `format` change retains a prior approval or cross-family attestation across a changed `revisionDigest`, (b) media bytes uploaded at publish time can differ from the approved `media[].sha256` byte digest without refusal, (c) the executor trusts a caller-supplied `reviewerFamily` instead of deriving the reviewer's sender identity and model family from the cited `reviewerMessageId` through Fleet/roster authority, or (d) an interrupted `publishing` or `unresolved` attempt issues a second platform write, resets to `queued` on a negative recent-posts search, or is bypassed by a new digest without operator reconciliation.

## Rejected Alternatives & Avoided Traps

- **Hardcoding `@tobiu` or `hypothesis` as unconditional product-schema rules:** The Fleet Manager is a product (@neo-fable-clio, [`#1261#issuecomment-6390768971`](https://github.com/neomjs/neo-agent-brain/pull/1261#issuecomment-6390768971); @neo-gpt-sophie, [`#1261#pullrequestreview-5640595551`](https://github.com/neomjs/neo-agent-brain/pull/1261#pullrequestreview-5640595551)). The normative recipient (`§1.6`) and switch writer (`§3.1`) resolve from the Fleet's registered operator principal (with `@tobiu` as Neo's Fleet binding), and `hypothesis` (`§1.2`) is governed by the Fleet policy flag `requireHypothesis` (defaulting to `true` for Neo's Fleet and required by working rule for `neomjs/neo#19575`).
- **Restating a non-existent Fleet custody ADR:** `learn/agentos/decisions/` has no prior custody ADR; `0042` records that absence explicitly and binds `<userData>/brain/fleet` (`neomjs/neo-agent-institution#345` / `#346`) in §2 rather than inventing or duplicating a prior record.
- **Deciding X's reply classification by inference or trusting a caller's `'link-reply'` label:** Recorded as Falsifier 1 with `https://help.x.com/en/rules-and-policies/x-automation` as the primary verification source, keeping `reply(...)` disabled and requiring `publish(...)` to verify same-account ownership of `inReplyTo` for `format: 'link-reply'` (`§4.2`, `§4.4`).
- **Storing the switch in UI component state:** Any Neo.mjs component property is reachable via the Neural Link (`InstanceService#assertWritable` is a multi-writer lock, not an auth boundary — @neo-opus-ada, [`18855553`](https://github.com/neomjs/neo/discussions/19500#discussioncomment-18855553)); the switch lives in Fleet custody behind an operator-authenticated write (`§3.1`).
- **Using caller-supplied `task.id` or a per-seat counter as request identity:** `task.id` is optional caller metadata (@neo-gpt-euclid, [`18856122`](https://github.com/neomjs/neo/discussions/19500#discussioncomment-18856122)) and a per-seat counter collides across harness instances (@neo-opus-ada, [`18855553`](https://github.com/neomjs/neo/discussions/19500#discussioncomment-18855553)); the mailbox-minted `MESSAGE:<uuid>` is the sole identity (`§1.3`).
- **Allowing an approval or attestation to survive an Edit, a format change, mutable media bytes, or a forged `reviewerFamily`:** `revisionDigest` covers `{account, channel, format, text, media, inReplyTo}` including each media item's `sha256` byte digest; the reviewer's family is derived from the cited review message via Fleet/roster authority; and an Edit creates a new revision inheriting neither approval nor attestation (@neo-gpt-sophie, [`18856006`](https://github.com/neomjs/neo/discussions/19500#discussioncomment-18856006), [`18856057`](https://github.com/neomjs/neo/discussions/19500#discussioncomment-18856057), and [`#1261#pullrequestreview-5640595551`](https://github.com/neomjs/neo-agent-brain/pull/1261#pullrequestreview-5640595551); `§1.2`, `§1.4`, `§3.2`).
- **Splitting publication state across two writers or treating negative recent-posts search as proof of non-publication:** `MailboxService` is the sole durable publication-state writer with an atomic `queued → publishing` reservation, and an interrupted `publishing` attempt that is not positively observed in recent posts transitions to terminal `unresolved` (`§1.5`, `§4.2`, `§4.3`).
- **Creating a new `request-publish` or `outbound-post` skill:** Rejected in `D#19500` OQ-3 (@neo-opus-ada `STEP_BACK` point 8, [`18854629`](https://github.com/neomjs/neo/discussions/19500#discussioncomment-18854629)) and `neomjs/neo-agent-skills#168`; `blog-post` is widened with load-on-demand `references/outbound-post.md` so router loaded-bytes stay flat.
- **Giving seats a Social-MCP server (`neomjs/neo-agent-brain#123` Leaf 3's April framing):** Superseded so no seat ever holds publish authority.
